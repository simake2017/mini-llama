# 技术篇 05：KV 缓存与增量生成

> 主题：为什么生成下一个 token 时不必重新计算全部历史位置。
> 依据：KVCache、Model::forward_token、src/main.cpp。
> 上游基准：llama.cpp @ 88b47a755；规范：tech-doc v1.1。

## 1. 缓存保存什么

注意力每层都会产生 K 和 V。当前位置之后，旧位置的 K/V 不会改变，因此可以保存起来。下一轮只计算新 token 的 Q、K、V，用新 Q 与缓存中的全部 K 做匹配，再读取对应的 V。

缓存不是模型文件，也不是跨进程的会话记录。它只存在当前 CLI 进程中，进程退出后消失。

## 2. 两个阶段

### Prefill

程序先把输入 token 按位置逐个送入前向。例如输入 `Hi` 会先编码，再处理位置 0、位置 1。每个位置都写入各层 K/V；最后一个输入位置的 logits 用于选择第一个生成 token。

### Decode

每轮采样得到一个新 token，程序把它送入一次前向。新位置读取之前的缓存并追加自己的 K/V，输出下一轮 logits。流程如下：

```text
输入 token 0 → 写入位置 0
输入 token 1 → 读取位置 0，写入位置 1，得到首个 logits
采样 token 2 → 读取位置 0、1，写入位置 2，得到下一组 logits
采样 token 3 → 读取位置 0、1、2，写入位置 3
```

这里的 token 编号和文字只是原理示意，真实编号由模型词表决定。

## 3. 当前实现的容量与布局

KVCache 预先分配固定容量，逻辑上按“层 → 位置 → 向量维度”布局 K 和 V。以某一层某一位置为例，地址基准可理解为：

```text
(layer * capacity + position) * kv_dim
```

每层的 K、V 都需要保存。`kv_dim` 是 K/V 头数乘每头维度，因此 GQA 模型的缓存通常比保存所有查询头更小。

写入一个位置时，append 会复制该位置的 K、V 向量。只有最后一层完成写入后，逻辑 size 才增加 1，这样所有层对“已完成的位置”保持一致。容量用尽时不能继续无限增长，必须在限制内结束或报错。

内存占用随层数、容量、kv_dim 和 K/V 两份数据增长，粗略为：

```text
2 * n_layer * capacity * kv_dim * sizeof(float)
```

实际分配还取决于类型和容器实现；本项目当前缓存使用 float 数组。

## 4. 历史实例：prefill Hi

业务线 `prefill` 使用预设 prompt `Hi`，历史运行观察到：

```text
第 0 层位置 0 的 K 向量模 = 1.3779
第 0 层位置 0 的 V 向量模 = 0.080459
最大逐元素差 = 0
clear 后复用的最大差 = 0
```

这些值说明该输入确实写入了非零 K/V，并且该线中的比较通过。它不是所有模型、所有 prompt 的固定结果，也不能单独证明完整前向与上游逐元素一致。

## 5. clear 与复用

清空缓存改变的是当前运行的逻辑状态，之后可以从新输入的位置 0 开始写入。它不是把 GGUF 文件改写，也不等于每次都重新分配模型权重。复用前必须保证旧位置不会被新序列读取。

## 6. 一致性和边界

增量路径与重新处理完整前缀的结果接近，是检查缓存接入是否合理的一种方法；但如果两条路径调用的是同一套有问题的前向代码，比较相等只能说明两条路径行为一致，不能独立证明数值正确。更强的验证还需要独立参考实现、已知输入和分层比较。

缓存容量不足、层数或维度配置不匹配时，应停止当前推理；只重复执行不会修复固定容量或模型配置问题。缓存不支持无限上下文，不实现跨进程持久化、分页缓存或多序列服务。
