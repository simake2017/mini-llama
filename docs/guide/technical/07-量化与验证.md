# 技术篇 07：量化与验证

> 主题：低精度权重怎样节省存储，以及怎样验证本项目的计算。
> 依据：src/quant.cpp、src/model.cpp、tests/arbiter.py。
> 上游基准：llama.cpp @ 88b47a755；规范：tech-doc v1.1。

## 1. 为什么模型权重可以压缩

F32 用 32 位浮点数保存一个值，数值范围和精度较高，但占空间较多。量化把一组浮点值用低位整数和缩放参数表示，读取时再近似还原为浮点数参与计算。它主要降低权重存储量；量化本身不等于更快，速度还受解码实现、CPU 指令、内存带宽和缓存影响。

## 2. Q8_0 原理实例

Q8_0 每块包含 32 个权重量化值和一个 16 位 scale。解码时将整数量化值乘 scale，得到近似浮点权重。忽略结构体对齐时，一块占 2 + 32 = 34 字节，而 32 个 F32 占 128 字节。

原理示例：若 scale 为 0.01、某个量化值为 25，该值近似还原为 0.25。真实块还要考虑具体类型的编码约定和舍入误差。

Q4_K、Q5_K、Q6_K 使用更复杂的分组 scale/min 等参数布局，不能套用 Q8_0 的“一个 scale 加 32 个整数”结构。不同类型必须使用各自的块布局解码。

## 3. 混合精度与近似性

文件名包含 Q8_0，不代表全部张量都是 Q8_0。历史 TinyLlama 文件有 45 个 F32 张量、156 个 Q8_0 张量。加载器按每个张量记录的类型选择解释方式；例如归一化权重可以保留 F32。

反量化只能得到近似值，不会恢复量化前丢失的精度。不同量化等级通常在体积、误差和运算开销之间权衡；不能只根据位数断言实际生成速度或质量。

## 4. 验证分层

| 层次 | 检查什么 | 能说明什么 | 不能单独说明什么 |
|---|---|---|---|
| 格式与块解码 | 字节布局、scale、边界 | 解码符合测试向量 | 整个模型前向正确 |
| 算子或张量 | 选定输入下的中间结果 | 局部计算差异范围 | 所有模型和输入均正确 |
| 前向参考对拍 | 与独立实现比较中间张量/logits | 覆盖输入下的数值接近程度 | 未覆盖的架构、权重和参数 |
| 端到端生成 | 输出是否可运行、有无异常 | CLI 主链路可走通 | 语言质量或事实正确性 |

本项目的 `tests/arbiter.py` 是 NumPy 前向参考工具，需提供模型路径和 token 列表；它只覆盖实现范围内的 LLaMA 风格前向。业务线中的增量/全量对比若调用同一套前向代码，不能充当独立正确性证明。

## 5. 历史结果与运行限制

历史测试曾报告 ctest 7/7 通过，其中 lines_model 约 74 秒。该结果是当时代码和环境的记录，不是本次文档修改后重新执行的结果。当前文档变更没有改动量化实现，也没有重新跑长时模型测试。

真实模型推理受 CPU、内存带宽、模型文件、构建选项和上下文长度影响。小模型、短 prompt 或 Q8_0 并不保证固定速度；mmap 也不代表所有权重已驻留内存。

## 6. 异常与边界

不支持的量化类型、截断的量化块或张量形状不匹配会导致加载/计算失败。修正模型文件或选择受支持类型后才值得重试。量化生成、训练、GPU 加速与任意 GGUF 架构执行不属于本项目范围。

代码入口见 [量化单元文档](../../05-quantization.md) 与 `src/quant.cpp`。验证时应保留模型、输入 token、参数、实际数值差异和运行环境，避免只记录“通过”。
