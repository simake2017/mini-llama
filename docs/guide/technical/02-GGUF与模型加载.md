# 技术篇 02：GGUF 与模型加载

> 主题：磁盘中的模型怎样变成可供前向计算使用的数据。
> 依据：GgufFile::load/parse、Model::load 与 docs/01、03。
> 上游基准：llama.cpp @ 88b47a755。
> 规范：tech-doc v1.1；示例注明历史实测或原理示例。

## 1. 文件里装了什么

GGUF 不是只有一块权重数组。它同时保存解释模型所需的信息：

| 部分 | 内容 | 作用 |
|---|---|---|
| 文件头 | 魔数、版本、张量数、元数据数 | 判断格式并确定解析规模 |
| 元数据 | 架构、维度、层数、词表等 | 确定数字应怎样解释 |
| 张量表 | 名字、维度、类型、偏移 | 找到具体权重 |
| 数据区 | 各张量的实际字节 | 前向计算读取的数据 |

张量是带形状的数字集合。二维张量可理解成矩阵；GGUF 中的量化类型还决定这些字节怎样解包。

## 2. 正常加载过程

打开文件并 mmap → 解析头 → 读取元数据 → 读取张量表 → 确定数据区 → 用元数据构造超参 → 按名字查找各层权重。

GgufFile 处理通用格式；Model::load 负责 LLaMA 风格网络如何使用这些张量。Tokenizer::load 从同一文件的元数据装载词表。能解析 GGUF 不等于能计算文件内任意架构。

mmap 建立虚拟内存映射，访问时仍涉及页面调入与内存带宽；它不保证大模型已全部驻留物理内存，也不承诺毫秒级完成全部加载。量化和类型转换过程仍会使用计算缓冲区。

## 3. 历史实测实例

```bash
MINILLAMA_MODEL=models/TinyLlama-1.1B-Chat-v1.0.Q8_0.gguf ./build/mini-llama-lines model_load
```

历史观察：

```text
GGUF 版本 = 3
张量数 = 201
对齐字节 = 32
general.architecture = llama
类型分布 F32 × 45
类型分布 Q8_0 × 156
层数 n_layer = 22
维度 n_embd = 2048
注意力头 n_head = 32
```

这说明文件名中的 Q8_0 不等于“所有张量都用 Q8_0”。归一化权重等仍可以是 F32。

同次运行显示 output.weight 的维度为 {2048,32000}。在该格式中最快变化的维度在前；这里对应输入维 2048、输出词表大小 32000。前向输出头把隐藏向量映射成每个候选编号的分数。

## 4. 按名字而不是按顺序找权重

历史模型的张量表第一个是 output.weight。程序不能假定“第一个张量一定是词嵌入”。例如 blk.0.attn_q.weight 表示第 0 层查询投影的权重；Model::load 根据约定名字和形状组织网络。

原理示例：张量表给出名字、偏移和类型，访问器返回相应字节；这里的偏移不是把“第几个张量”乘以固定长度，因为张量大小与类型不同。

## 5. 异常、状态与边界

| 异常 | 处置 | 重试条件 |
|---|---|---|
| 文件无法打开 | 加载失败，CLI 返回错误 | 修正路径或权限 |
| 魔数错误或文件截断 | 解析失败，不继续计算 | 换完整有效文件 |
| 缺少必要元数据或权重 | 无法建立可用模型 | 换兼容文件或扩展实现 |
| 权重类型或形状不支持 | 报错 | 不能靠重复执行修复 |

本主题只读原始模型文件，不实现 GGUF 写入、模型训练或量化文件生成。部分防御校验与上游不同，不能把教学解析器当作已完成全面加固的文件验证器；已知差异见 docs/01 的 §16.2。
